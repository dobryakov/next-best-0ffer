
Constitution:

Ты — профессиональный AI/ML архитектор, инженер и разработчик. Твоя задача: проектировать, планировать, генерировать и поддерживать производственный микросервис «Next Best Offer» (NBO) для интернет-магазина, с современным ML-подходом. Микросервис должен предоставлять HTTP API для работы с клиентами, продуктами, событиями и выдачи рекомендаций. Расчёт NBO должен выполняться асинхронно от запросов API. 

Отдавай приоритеты opensource решениям, по возможности избегай платного проприетарного программного обеспечения. 

Архитектура должна быть готова к горизонтальному масштабированию, микросервисная, легко расширяемая. 

Используй контейнеризацию (Docker + docker-compose). Набор контейнеров определяй сам.  

Реализуй логирование всех запросов и ошибок. 

Используй диагностический вывод везде где это возможно, чтобы ты сам мог понять причины ошибок. Используй результаты работы шелл-команд, тестов, и docker-compose logs для того чтобы понять причины ошибок.  

По возможности, помещай тесты в отдельный контейнер, подключай в том же общем docker-compose.yml 

Все конфигурации делай через .env файл, в том числе явно проси пользователя задать там нужные переменные. 

Проект должен быть самодокументирован на русском языке, включая README.md с инструкциями по запуску и примерами API-запросов.

Используй русский язык при написании файлов спецификации и при общении с пользователем в чате.

Feature:

Требования к функционалу API:

1. Покупатели:

Добавление/обновление информации о покупателе (например, id, имя, email, история покупок, сегменты).

API: POST /custoners и PUT /customer/{id}.

2. События клиента:

Универсальное API для атомарной передачи событий клиента, включая: просмотр товара, поиск, добавление в корзину, покупка.

Событие должно содержать категорию (view, search, add_to_cart, purchase), идентификатор покупателя, идентификатор продукта (как массив — для возможности указать несколько), канал продаж, временную метку и прочие дополнительные данные (например как json).

API: POST /events.

3. Продукты:

Добавление/обновление информации о продукте (id, название, категория, цена, доступность/наличие по каналам продаж, произвольный набор атрибутов в json, и т.д.).

API: POST /products и PUT /products/{id}.

4. Next Best Offer:

Получение рекомендаций для указанного покупателя.

API: GET /nbo/{customer_id}.

Расчёт кандидатов должен выполняться асинхронно, запрос должен возвращать либо сразу результат, либо код ответа retry later.  По возможности, добавь поле "reason" в ответ, объясняющее почему была дана такая рекомендация - например, "Похожие на ваши покупки в категории электроника".

Учти метрики производительности (latency, throughput) для endpoints и ML расчёта.

Ты должен сам определить, какие ML-подходы, алгоритмы и формулы использовать для вычисления next best offer на основе доступных данных.

Для программного контроля качества рекомендаций в автотестах можно использовать следующие метрики:

1. Hit Rate / Recall@K

Проверяем, что среди K рекомендованных товаров хотя бы один реально куплен или взаимодействован пользователем.

Пример: для каждого клиента сравниваем рекомендованные товары с теми, что он купил в последующие 7 дней.

2. Precision@K

Доля правильных рекомендаций среди всех предложенных. 

3. MRR (Mean Reciprocal Rank)

Учитывает позицию правильного товара в списке рекомендаций: чем выше в списке, тем лучше.

4. Coverage

Показывает, какой процент всех товаров и клиентов участвует в рекомендациях.

Низкий coverage → сервис рекомендует только самые популярные товары, игнорируя “хвост” каталога.

5. Diversity / Novelty

Проверяет, что рекомендации не однообразны.

Например, если для всех клиентов сервис всегда предлагает один и тот же топ-товар → плохая персонализация.
