# Phase 0 Research — Next Best Offer API

## ML Подход

- **Decision**: Двухэтапная архитектура рекомендаций: генерация кандидатов коллаборативной фильтрацией (ALS по матрице customer × product) и ранжирование кандидатов градиентным бустингом (LightGBM) на признаках из feature store.
- **Rationale**: ALS устойчив при разреженных данных, быстро обновляется инкрементальными событиями и хорошо покрывает long-tail. LightGBM даёт высокую точность ранговых задач, позволяет учитывать бизнес-правила (наличие товара, маржинальность) и легко обучается офлайн с периодическими обновлениями.
- **Alternatives considered**:
  - Item-to-item cosine similarity + правила — просто, но не учитывает персонализацию.
  - Нейросетевые sequence-to-sequence модели (SASRec) — повышают качество, но требуют длительного обучения и GPU, что не соответствует срокам фичи.

## Candidate Generation Refresh

- **Decision**: Обновление матрицы взаимодействий раз в час батчевой задачей, плюс онлайновое добавление свежих событий через implicit ALS partial_fit.
- **Rationale**: Баланс между качеством и ресурсами; позволяет учитывать свежие сессии без полной переобучаемости.
- **Alternatives considered**:
  - Полный пересчёт раз в сутки — риски устаревания рекомендаций.
  - Только онлайновое обновление — более сложная поддержка стабильности модели.

## Feature Store

- **Decision**: Использовать Feast поверх PostgreSQL/Redis, хранить агрегаты по покупателю, по товару и кросс-особенности (frequency, recency, monetary, popularity, сезонность).
- **Rationale**: Feast уже стандартизирован в конституции, обеспечивает консистентность признаков между обучением и продакшеном, легко интегрируется с Python-стеком.
- **Alternatives considered**:
  - Ручное управление признаками в PostgreSQL — повышает риск дрейфа признаков.
  - MLflow Feature Store — избыточно для стартового этапа.

## Business Constraints

- **Decision**: Rerank после LightGBM для фильтрации товаров вне наличия, с запретом повторного предложения уже купленных SKU в текущем окне 7 дней; поддержка каналов продаж через фильтрацию по `channel`.
- **Rationale**: Соответствует требованиям spec, уменьшает негативный опыт пользователя.
- **Alternatives considered**:
  - Встраивать фильтрацию внутрь модели — усложняет обучение и ухудшает переносимость.

## Observability & Experimentation

- **Decision**: Логирование inference метрик (score, reason), отправка результатов A/B тестов в PostgreSQL, мониторинг качества через ежедневные отчёты HitRate@5, Precision@5, MRR.
- **Rationale**: Соответствует Принципу III и V конституции; обеспечивает прозрачность ML-качества.
- **Alternatives considered**:
  - Ограничиться техническими метриками API — не покрывает эффективность рекомендаций.
