# Feature Specification: Next Best Offer API

**Feature Branch**: `001-define-nbo-api`  
**Created**: 2025-11-09  
**Status**: Draft  
**Input**: User description: "Добавление/обновление покупателей и продуктов, единый сбор событий клиентов, выдача Next Best Offer через REST-эндпоинты (POST /customers, PUT /customer/{id}, POST /events, POST /products, PUT /products/{id}, GET /nbo/{customer_id}) с асинхронной обработкой и пояснением рекомендаций."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Управление данными покупателя (Priority: P1)

Менеджер по CRM обновляет профиль покупателя, чтобы персонализировать коммуникации и учесть свежую информацию (id, контакты, сегменты).

**Why this priority**: Без актуальных данных о покупателе невозможны корректные рекомендации и сегментация, это фундамент для остальных сценариев.

**Independent Test**: Отправить запрос на создание/обновление покупателя с обязательными и дополнительными полями и проверить, что данные доступны для последующих запросов.

**Acceptance Scenarios**:

1. **Given** внешний CRM передаёт полные данные нового покупателя, **When** выполняется POST `/customers`, **Then** система сохраняет запись, подтверждает создание и фиксирует операцию в логах.
2. **Given** данные покупателя изменились, **When** выполняется PUT `/customer/{id}` с обновлёнными полями, **Then** система применяет изменения, возвращает актуализированное состояние и сохраняет версию для аудита.

---

### User Story 2 - Регистрация клиентских событий (Priority: P2)

Цифровой канал продаж передаёт атомарные события поведения покупателя (просмотр, поиск, добавление в корзину, покупка), чтобы система могла учитывать их в расчётах предложений.

**Why this priority**: События напрямую влияют на качество рекомендаций и позволяют отслеживать активность клиента в near real-time.

**Independent Test**: Сымитировать отправку разных категорий событий через POST `/events` и проверить их в хранилище и в очереди расчёта предложений.

**Acceptance Scenarios**:

1. **Given** событие просмотра товара с идентификаторами покупателя и SKU, **When** канал вызывает POST `/events`, **Then** система валидирует обязательные поля, подтверждает приём и ставит событие в очередь обработки.
2. **Given** событие покупки с несколькими товарами, **When** канал отправляет массив product_id, **Then** система сохраняет все позиции и связывает их с заказом для последующего анализа.

---

### User Story 3 - Получение Next Best Offer (Priority: P3)

Цифровой ассистент получает рекомендацию для покупателя, чтобы вывести персональное предложение и объяснить его с помощью человеко-понятной причины.

**Why this priority**: Результат расчётов — основная бизнес-ценность, позволяющая повысить конверсию и удержание.

**Independent Test**: Выполнить GET `/nbo/{customer_id}` для разных статусов расчёта и убедиться, что ответ содержит рекомендацию или корректный сигнал о необходимости повторного запроса.

**Acceptance Scenarios**:

1. **Given** для покупателя рассчитаны предложения, **When** выполняется GET `/nbo/{customer_id}`, **Then** система возвращает список кандидатов с полем `reason`, отражающим основную причину выбора.
2. **Given** расчёт ещё в процессе, **When** ассистент запрашивает предложение, **Then** система отвечает кодом ретрая (например, 202) и включает прогнозируемое время готовности.

---

### Edge Cases

- Отсутствует обязательный идентификатор покупателя или продукта в событии — запрос отклоняется с пояснением и логируется как ошибка валидации.
- Поступает событие с дублирующейся временной меткой и идентичным payload — система должна обеспечить идемпотентность и не создавать повторных расчетов.
- Для запроса рекомендаций отсутствуют актуальные данные или покупатель не найден — система возвращает информативный ответ об отсутствии кандидатов и совет по пополнению данных.
- Массовая загрузка продуктов или покупателей превышает лимиты — операции должны ставиться в очередь или возвращать управляемые ошибки с указанием квот.
- Канал отправляет событие с `product_id`, которого ещё нет в каталоге — событие принимается и попадает в очередь обработки, но downstream-компоненты не смогут обогатить запись признаками товара, поэтому такие SKU следует дозагружать в `products` как можно быстрее.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: API ДОЛЖЕН предоставлять REST-эндпоинты для создания и обновления покупателей: POST `/customers` и PUT `/customer/{id}` с валидацией обязательных полей и поддержкой пользовательских атрибутов.
- **FR-002**: API ДОЛЖЕН предоставлять REST-эндпоинты для создания и обновления продуктов: POST `/products` и PUT `/products/{id}` с проверкой наличия по каналам продаж и произвольных атрибутов.
- **FR-003**: API ДОЛЖЕН принимать универсальные клиентские события через POST `/events`, поддерживая категории `view`, `search`, `add_to_cart`, `purchase`, множественные product_id и обязательную временную метку.
- **FR-004**: Система ДОЛЖНА обеспечивать идемпотентность для повторной отправки событий и запросов обновления, генерируя детерминированный идентификатор на основе временной метки и содержимого payload, сохраняя недавнюю историю и предотвращая повторную обработку дублей.
- **FR-005**: Расчёт Next Best Offer ДОЛЖЕН выполняться асинхронно, а GET `/nbo/{customer_id}` обязан возвращать готовые рекомендации либо код ретрая с указанием условий повторного запроса.
- **FR-006**: Ответ с рекомендациями ДОЛЖЕН содержать поле `reason`, предоставляющее человеко-понятное объяснение выбора каждого предложения.
- **FR-007**: Все эндпоинты ДОЛЖНЫ логировать trace id, входные параметры и результат, а также предоставлять health-check для мониторинга доступности.
- **FR-008**: Все конфигурационные параметры (лимиты, таймауты, маппинги каналов) ДОЛЖНЫ выноситься во внешние управляемые настройки окружения и сопровождаться описанием в README/спецификации.
- **FR-009**: Сервис ДОЛЖЕН возвращать структурированные ошибки с кодами и пояснениями, чтобы внешние клиенты могли корректно обрабатывать сбои и повторять операции.

### Key Entities *(include if feature involves data)*

- **Покупатель (Customer)**: Представляет конечного клиента; ключевые атрибуты — идентификатор, контактные данные, сегменты, история покупок, пользовательские свойства.
- **Продукт (Product)**: Каталоговая позиция; ключевые атрибуты — SKU, категория, цена, доступность в каналах, произвольные атрибуты.
- **Событие (Event)**: Атомарное действие клиента; атрибуты — категория события, customer_id, массив product_id, канал, timestamp, дополнительные данные.
- **Предложение (OfferRecommendation)**: Результат расчёта Next Best Offer; атрибуты — список рекомендуемых продуктов, поле `reason`, метаданные о времени и источнике расчёта, статус готовности.

## Assumptions

- Внешние системы аутентифицированы и авторизованы вне рамок данной спецификации (например, через корпоративный API-шлюз).
- Лимиты и SLA для количества запросов будут согласованы с командами интеграции и могут быть уточнены на этапе планирования.
- Источник данных для расчёта рекомендаций (ML-модели, правила) уже существует или развивается параллельно и предоставляет результаты в очередь или хранилище.
- Партнёры могут начинать отправлять события до полной загрузки каталога, однако рекомендуется минимально синхронизировать импорт товаров и событий (например, ежедневными дельтами), чтобы рекомендации опирались на актуальные описания SKU.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% запросов к POST/PUT эндпоинтам завершаются с подтверждённым сохранением данных менее чем за 2 секунды при номинальной нагрузке.
- **SC-002**: Минимум 90% ответов GET `/nbo/{customer_id}` содержат заполненное поле `reason`, описывающее главную причину рекомендации.
- **SC-003**: Не менее 85% запросов на рекомендации получают готовый результат с первого обращения; оставшиеся получают корректный сигнал на повторный запрос в пределах 30 секунд.
- **SC-004**: Интеграционные тесты покрывают все пользовательские истории и edge-case сценарии, демонстрируя успешные и ошибочные пути.

## Clarifications

### Session 2025-11-09

- Q: Каким образом система должна обеспечивать идемпотентность при повторной отправке событий внешними каналами? → A: Сервис генерирует идентификатор из timestamp и payload, используя его для блокировки дублей.
- Примечание: До появления выделенного тестового контейнера контрактные и интеграционные тесты временно запускаются внутри контейнера `api`; после добавления отдельного окружения запуск будет вынесен согласно конституции.
