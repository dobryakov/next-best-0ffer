## Core Principles

### Принцип I. Продуктовая ML-микросервисная архитектура

- Сервис NBO реализуется как совокупность независимых контейнеризованных компонентов: публичное HTTP API, асинхронные воркеры расчёта, pipelines подготовки данных и ML-инфраструктура.
- Расчёт рекомендаций выполняется асинхронно от запросов API через очередь задач; `GET /nbo/{customer_id}` возвращает готовый ответ с полем `reason` или код повторной попытки с инструкцией клиенту.
- Все API соответствуют REST, поддерживают идемпотентность, корректные коды ответов и расширяемые контрактные схемы.

Обоснование: устойчивый микросервисный дизайн и асинхронность позволяют масштабировать NBO по нагрузке и развивать ML-компоненты независимо.

### Принцип II. Контейнеризация и открытая инфраструктура

- Все сервисы, клиенты, тестовые раннеры и вспомогательные инструменты разворачиваются через `docker-compose.yml`; на хост-машине отсутствуют обязательные зависимости.
- По умолчанию предполагается отсутствие интерпретаторов (Python, Node.js, PHP, Ruby и др.) на хост-машине; при необходимости выполнения скриптов интерпретаторы запускаются внутри соответствующих контейнеров без установки на хост.
- Используются только opensource-решения для вычислений, хранения данных, очередей, feature store и ML-life-cycle (например, FastAPI/Express, PostgreSQL, Redis, Feast, MLflow, Prefect).
- Тесты и клиентские SDK (JS, PHP, shell) находятся в отдельных контейнерах и могут запускаться автономно.

Обоснование: контейнеризация гарантирует воспроизводимость, а opensource-стек снижает стоимость владения и исключает блокировки от закрытых платформ.

### Принцип III. Наблюдаемость и диагностируемость

- Все запросы, ошибки и фоновые задачи логируются в структурированном формате с обязательными trace id, метаданными канала, устройства и customer_id.
- Каждый ключевой сервис экспонирует health-check endpoints и метрики (latency, throughput, глубина очереди, качество рекомендаций) для мониторинга.
- Диагностические команды, docker-compose logs и скрипты предоставляются для расследования инцидентов; при добавлении функционала расширяются и логи.

Обоснование: полноценная наблюдаемость позволяет оперативно находить узкие места и подтверждать качество рекомендаций в продакшене.

### Принцип IV. Управляемая конфигурация и документация

- Все конфигурации читаются из `.env`, значение каждой переменной описано в README/справочниках; при добавлении переменных требуется инструкция по их настройке.
- Документация и спецификации ведутся на русском языке, включают примеры curl и скриптов, описание ML-алгоритмов для бизнеса и руководства по запуску.
- Любые изменения API, конфигураций и процессов сопровождаются актуализацией README, quickstart, contracts и комментариями к миграциям.

Обоснование: прозрачная конфигурация и документация снижают риск ошибок при развёртывании и обеспечивают доступность знаний всей команде.

### Принцип V. Качество, тестирование и эксперименты

- Юнит-, интеграционные и нагрузочные тесты обязательны для всех компонентов; автогенерация синтетических данных поддерживает масштаб 100k товаров и 10k покупателей.
- Для разных классов тестов выбираем подходящее окружение:
  - встроенные unit-тесты фреймворков запускаются в соответствующих контейнерах сервисов;
  - тесты HTTP API и браузерные (e2e, Playwright) выполняются в отдельном тестовом контейнере;
  - все тестовые контейнеры подключаются в общий `docker-compose.yml`.
  При необходимости набор контейнеров расширяется по усмотрению команды.
- ML-качество контролируется по метрикам HitRate@K, Precision@K, MRR, Coverage, Diversity и предложенным дополнениям; результаты фиксируются в ML metadata store.
- A/B тестирование (`variant=A/B`) встроено в API, реакции пользователей (click/purchase) записываются для обучения и анализа uplift.

Обоснование: строгая дисциплина тестирования и экспериментов обеспечивает проверяемость гипотез и устойчивое развитие продукта.

## Технологические стандарты

- Бэкенд реализуется на Python (FastAPI) или Node.js (Express) с соблюдением REST и асинхронной обработки NBO; расширения согласуются через архитектурное ревью.
- Основное хранилище — PostgreSQL; Redis (или эквивалент) используется для кэширования, хранения событий и очередей; возможно подключение векторных/feature store при сохранении opensource-лицензий.
- Очереди задач (например, RQ, Celery, BullMQ) обеспечивают асинхронность, масштабируемость воркеров и SLA обработки.
- Feature store и ML metadata tracking (Feast, MLflow, таблицы в БД) обязательны при внедрении моделей; версии моделей, дата обучения и метрики фиксируются.
- Реализация клиентов (JS, PHP, shell) и вспомогательных скриптов выполняется в отдельных контейнерах; все скрипты поддерживают трассировку и конфигурацию через `.env`.
- Все endpoints предоставляют примеры использования и включают поле `reason`, поясняющее бизнес-логику рекомендуемого предложения.

## Рабочий процесс и соответствие

- Перед началом работы каждая feature проходит раздел "Constitution Check" в плане; несоответствия фиксируются в таблице Complexity Tracking с обоснованием.
- Тесты запускаются в контейнерах, определённых в `docker-compose.yml`; пайплайн CI/CD использует те же образы.
- При изменении API, данных или конфигураций обязательна актуализация документации, схем контрактов и `.env.example`.
- Логи и метрики исследуются через предоставленные скрипты; результаты расследований фиксируются в документации или постмортем.
- Любые сервисы, завязанные на нестандартные порты, документируются вместе с правилами проксирования через фронтенд-контейнеры.

## Governance

- Конституция обладает высшей силой: архитектурные решения, планы и код-ревью проверяются на соответствие всем принципам.
- Изменения в конституции оформляются через pull request с анализом влияния, обновлением зависимых шаблонов и bump версии по SemVer (MAJOR — несовместимые изменения, MINOR — новые принципы/существенные дополнения, PATCH — уточнения формулировок).
- Каждое существенное изменение сервиса сопровождается проверкой планов, спецификаций и task-листов на соблюдение принципов и технологических стандартов.
- Команда поддерживает health-checks, мониторинг и журналы аудита; нарушения принципов документируются и устраняются до релиза.
- Ежеквартально проводится аудит соответствия (обновление документации, списков переменных, тестовых скриптов) с фиксацией результатов.
